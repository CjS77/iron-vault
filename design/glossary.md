# Iron Vault glossary

One name per concept, in docs and code alike. Definitions follow the
[product specification](iron-vault-specification.md).

**Adding a term:** add it here before the code that uses it. Keep entries alphabetical, give one one-sentence
definition, name the owning bounded context, and cite the specification section that introduces it. Fill in the Rust
type once one exists.

## Bounded contexts

From [implementation spec §1](implementation-specification.md#1-implementation-structure). Each crate owns its model; crates do not reach
into each other's private storage models.

| Crate               | Owns                                                                                                    |
|---------------------|---------------------------------------------------------------------------------------------------------|
| `iron-vault-policy` | Caller grants, routes, slots, markers, and the final outgoing-request decision; pure, no I/O            |
| `iron-vault-kinds`  | Credential resolution, token lifecycle, and provider signing rules                                      |
| `iron-vault-store`  | Vault identity, recipient envelopes, record files, approval metadata, durable transactions and recovery |
| `iron-vault`        | Service binary, HTTP/admin interfaces, CLI client, config loading, deployment adapters and scrubbing    |
| `iron-vault-notify` | Desktop notification agent, from v1: shows owner notifications; no vault, config or admin access        |

## Actor disambiguation

| Term                   | Meaning                                                                                                                                         | Protected install                 | Development                             |
|------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------|-----------------------------------------|
| **Owner**              | The person at the end of the authority chain                                                                                                    | Alice, but only by passing `sudo` | Alice                                   |
| **Service account**    | The OS account that runs the service and owns its config (0600), vault and runtime directory. The code's `ExpectedOwner` is this account's uid. | `iron-vault`                      | Alice's login account                   |
| **Admin principal**    | An OS account the admin socket accepts, checked from the socket's peer credentials                                                              | root                              | the invoking user                       |
| **Login account**      | The owner's everyday OS account                                                                                                                 | `alice`, which has no authority   | the same account as the service account |
| **Host administrator** | Anyone who can become root, e.g. through `sudo`. Outside the threat model ([§2](iron-vault-specification.md#2-security-promise-and-limits)).    | Alice, if she's in sudoers        | not applicable                          |

Context notes for terms that span crates:

- **Credential:** `iron-vault-kinds` owns resolving a credential into request bytes; its encrypted form is the
  credential record in `iron-vault-store`.
- **Owner:** the binary's admin interface authenticates an admin principal, never the owner directly; store and policy
  only act on approved changes. See [Actor disambiguation](#actor-disambiguation).
- **Hardware key, Source:** `iron-vault-store` holds recipient envelopes and connector storage, so it owns both.
- **Upstream:** `iron-vault-policy` decides whether a request may go to an upstream; the binary performs transport.
