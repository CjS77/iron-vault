Your programs use the keys. They never hold them

Iron Vault is a small local proxy that holds your API credentials. Point an application's base URL at it and give the application a placeholder. Iron Vault adds the real key on the way out, over verified TLS.

Install Iron Vault Read the manual

The path of one request

Your application

Calls http://localhost/brave/… with a placeholder key. Holds at most a caller token that grants specific routes.

Iron Vault

  1. Authenticates the caller
  2. Checks the route's method, path and rate limit
  3. Adds the credential to a header or query parameter
  4. Scrubs the key from the response

Provider API

Receives the real key over HTTPS with verified TLS. Redirects are never followed with the credential attached.

What it does

Three locks between a program and your keys

An agent, an MCP server or a back-office app gets exactly the access it needs, and never a secret it could leak.

Credential injection

Applications never see the provider key. Iron Vault stores it, adds it to each request, and takes it back out of anything that echoes it.

  • Static API keys and Basic authentication
  • Placed in the header or query parameter the route names
  • Scrubbed from response headers, compressed bodies and streams
store a key
# prompted or piped, never an argument
pass show brave | iron-vault add brave \
  --origin api.search.brave.com

Restricted routes

Each caller gets only the routes it is granted. A key can only ever reach the hosts it was stored with, so editing a route can't send it anywhere else.

  • Callers identified by Unix account, caller token or isolated listener
  • Routes limited by credential, HTTP method, path and request rate
  • Permitted destinations sealed inside the encrypted credential
config.toml
[callers.dev]
listener = "local"
auth = "peer"     # the kernel names the account
user = "alice"
routes = ["venice-dev"]

Encrypted, approved, audited

The vault is encrypted at rest and every change to its rules needs your sign-off. A typed audit log records who did what, without ever writing a secret.

  • Credentials encrypted with age, plus an offline recovery key
  • Each config change signed with a strictly increasing approval version
  • Wrong passphrases trigger a cooldown from 30 s up to 15 min
day to day
iron-vault unlock          # vault passphrase
iron-vault recovery check  # the offline key still works
iron-vault lock            # secrets out of memory

Security boundary

What it promises, and what it doesn't

A security tool should be plain about its limits. These come straight from the specification.

Iron Vault stops a caller from

  • Reading a stored provider credential, even one it is allowed to use.
  • Sending a key to another origin than the ones it was stored with.
  • Using a route its identity isn't granted, or exceeding the route's rate.
  • Running an unapproved config, or replaying an old config with its old approval.

It can't stop

  • Misuse of a granted route. Malware that can read a caller's token can use that caller's routes, within its limits.
  • Every transformed secret. Scrubbing catches the credential's known forms, not every encoding of it.
  • A hostile administrator. Root and other host administrators are trusted.

Installation

Two ways to install

Try it as your own user in development mode, or install the protected service from a Debian package.

Development mode

try it out

Runs as your own user, with files in your XDG directories. Callers, routes, TLS, scrubbing, encryption and approvals all work as normal.

bash
git clone https://github.com/CjS77/iron-vault
cd iron-vault
cargo install --path crates/iron-vault --features dev-mode \
  --root ~/.local/iron-vault-dev
export PATH="$HOME/.local/iron-vault-dev/bin:$PATH"
chmod -R g-w ~/.local/iron-vault-dev

iron-vault serve --log-to-stdout   # in its own terminal
iron-vault init                    # two passphrases, one recovery key
iron-vault unlock
iron-vault status                  # service: ready

Development mode gives no isolation from malware running as you. It is for trying Iron Vault and for development. Full tutorial

Protected Linux

system service

Runs as the iron-vault system account, with the vault in /var/lib/iron-vault, out of reach of ordinary accounts. You administer it with sudo.

bash
cargo install cargo-deb --locked   # once
cargo deb -p iron-vault --locked
sudo apt install ./target/debian/iron-vault_*.deb
sudo iron-vault init
sudo iron-vault unlock

Harden sudo and encrypt swap and hibernation storage first. The package hasn't had a release check on a real machine yet. Installation guide

Requires Linux, Rust 1.98 (pinned in rust-toolchain.toml), and for the tutorial curl and jq. macOS and Windows services are on the roadmap.
